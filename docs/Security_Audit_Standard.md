# Security Audit Standard (Generic, Portable)

A comprehensive, project-agnostic security checklist aligned to industry
standards — OWASP Top 10 (2021), OWASP ASVS (Application Security
Verification Standard), OWASP API Security Top 10, CWE/SANS Top 25 Most
Dangerous Software Weaknesses, and NIST SP 800-53 / NIST Secure Software
Development Framework (SSDF) control families. It contains no
project-specific content — copy this single file into any codebase's
`docs/` folder and use it as-is.

**Intent**: if a codebase is built and *maintained* against every item here,
a later audit against this same checklist should find close to nothing.
This is a maintenance standard, not a one-time cleanup list — re-run it
whenever the codebase changes shape (new auth mechanism, new integration,
new data type handled) and periodically regardless (e.g. quarterly, or
before any major release).

## How to use this

1. Point an audit (yourself, a teammate, or an AI coding agent) at this file
   and ask it to run through every section against the actual codebase,
   citing real file paths/line numbers for each finding — never a generic
   "looks fine."
2. For each checklist item: mark it **Pass**, **Fail**, **N/A** (with a
   one-line reason it doesn't apply), or **Needs manual verification**
   (things a static read of the code can't fully confirm — e.g. "is TLS
   actually enforced at the load balancer").
3. Log every Fail/Needs-verification item in §16 (Findings Log) with a
   date, severity, and status. Don't delete resolved findings — mark them
   Fixed with a date so the log doubles as a history.
4. Severity scale used throughout: **Critical** (remote, unauthenticated,
   full compromise or data breach) / **High** (auth bypass, privilege
   escalation, significant data exposure) / **Medium** (requires
   preconditions, limited blast radius) / **Low** (defense-in-depth,
   hardening, best-practice gaps).

This checklist assumes a typical web application (frontend + backend +
database, possibly with third-party integrations). Skip sections that
genuinely don't apply (e.g. §11 File Uploads for an app with none) and mark
them N/A rather than deleting them — a future audit should see the section
was considered, not omitted.

## 1. Authentication

Maps to: OWASP ASVS V2, OWASP Top 10 A07:2021 (Identification &
Authentication Failures), CWE-287, CWE-798, CWE-521.

- [ ] Passwords are hashed with a modern, slow, salted algorithm — bcrypt,
      scrypt, or Argon2id. Never MD5/SHA1/SHA256 alone (too fast, brute-
      forceable), never reversible encryption, never plaintext.
- [ ] Password comparison uses a timing-safe/constant-time compare, not `==`
      or `===` on the hash output.
- [ ] Minimum password strength policy enforced server-side (length is the
      most effective single control — NIST 800-63B recommends ≥8 chars
      minimum, no forced complexity rules, no forced periodic rotation).
- [ ] No hardcoded credentials, API keys, or default passwords anywhere in
      source — grep for common patterns (`password =`, `apiKey =`,
      `secret =` followed by a literal string) and CI-gate this if possible
      (e.g. `git-secrets`, `trufflehog`, `gitleaks`).
- [ ] Every login failure returns a generic error — never reveal whether
      the *username* or the *password* was wrong (prevents account
      enumeration).
- [ ] Login is rate-limited / throttled per account and per IP, with
      exponential backoff or a temporary lockout after N failed attempts.
      Lockout itself shouldn't be usable as a DoS vector against a known
      username (consider CAPTCHA or increasing delay instead of hard
      lockout for public-facing auth).
- [ ] Multi-factor authentication (MFA/2FA) is available, and required for
      any admin/privileged account at minimum.
- [ ] Password reset flow: reset tokens are single-use, time-limited (e.g.
      ≤1 hour), cryptographically random (not predictable/sequential), and
      invalidated after use or after a new password is set. The "check your
      email" response is identical whether or not the email exists in the
      system.
- [ ] "Remember me" / persistent login tokens are not the same as the
      session token itself — a separate, revocable, hashed-at-rest token.
- [ ] Service-to-service and API authentication uses proper credentials
      (API keys, mTLS, OAuth client credentials) — never a shared static
      secret hardcoded in client-side code.
- [ ] SSO/OAuth/OIDC integrations validate the `state` parameter (CSRF
      protection for the auth flow) and validate the token signature/issuer/
      audience — never trust an unsigned or unverified token claim.

## 2. Session Management

Maps to: OWASP ASVS V3, CWE-384 (Session Fixation), CWE-613.

- [ ] Session identifiers are long, random, and generated by a
      cryptographically secure RNG — never sequential or predictable.
- [ ] Session cookies set `HttpOnly` (blocks JS/XSS access to the cookie),
      `Secure` (HTTPS-only transmission), and `SameSite=Lax` or `Strict`
      (CSRF mitigation) as a default, loosened only where a specific,
      documented reason requires it (e.g. `SameSite=None` for a legitimate
      cross-site embed, always paired with `Secure`).
- [ ] Session ID is regenerated on privilege change (login, logout,
      password change, role elevation) — prevents session fixation.
- [ ] Sessions expire after a reasonable idle timeout and an absolute
      maximum lifetime, appropriate to sensitivity (minutes for banking-
      grade, hours-to-days for a low-sensitivity app).
- [ ] Logout actually invalidates the session server-side, not just clears
      the client-side cookie — a captured token before logout shouldn't
      still work after.
- [ ] There's a way to revoke sessions (e.g. "log out all devices",
      or an admin-triggered forced logout) for compromised-account response.
- [ ] If sessions are stateless (JWT or similar signed token), there's a
      real revocation strategy (short expiry + refresh token rotation,
      or a denylist) — a bare stateless JWT with no revocation path and a
      long expiry is a known anti-pattern.

## 3. Access Control / Authorization

Maps to: OWASP Top 10 A01:2021 (Broken Access Control), OWASP ASVS V4,
CWE-862 (Missing Authorization), CWE-863 (Incorrect Authorization),
CWE-639 (IDOR).

- [ ] **Every** data-access/mutation entry point independently verifies the
      caller is authorized for *that specific action on that specific
      resource* — never assume "the UI hid the button" or "the page-level
      guard already checked" is sufficient. This is the single most common
      real-world access-control failure: a server action/API endpoint/RPC
      handler is reachable directly (its address/name is often visible in
      client bundles or network logs) even when no UI links to it.
- [ ] Object-level authorization (IDOR check): when a request includes an
      ID (order ID, user ID, document ID, etc.), the server confirms the
      *authenticated caller* owns or is permitted to act on *that specific
      ID* — not just that the ID exists. Test by substituting another
      valid ID belonging to a different account.
- [ ] Role/permission checks happen server-side, on every request, not
      cached client-side or trusted from a client-supplied claim (e.g.
      never trust a `role: "admin"` field sent in a request body).
- [ ] Authorization logic is centralized (a shared function/middleware/
      policy engine) rather than reimplemented ad hoc per route — ad hoc
      duplication is where checks get silently forgotten as the codebase
      grows. If it isn't centralized, that itself is a finding.
- [ ] Privilege escalation paths are tested: can a low-privilege user
      change their own role, or another user's role, via a
      profile-update endpoint that wasn't meant to allow it (mass-
      assignment vulnerability, CWE-915)?
- [ ] Default-deny posture: new routes/fields/actions require explicit
      authorization to be added, rather than being open by default until
      someone remembers to lock them down.
- [ ] Admin/back-office interfaces are not reachable without authentication
      even if "nobody would guess the URL" — no security through obscurity
      as the sole control.
- [ ] Multi-tenant systems: verify tenant isolation at the data-access
      layer itself (e.g. every query scoped by `tenant_id` derived from the
      authenticated session, never from a client-supplied parameter).

## 4. Input Validation & Injection Prevention

Maps to: OWASP Top 10 A03:2021 (Injection), CWE-89 (SQL Injection),
CWE-78 (OS Command Injection), CWE-79 (XSS), CWE-611 (XXE), CWE-502
(Insecure Deserialization), CWE-918 (SSRF).

- [ ] All database queries use parameterized statements / prepared
      statements / an ORM's parameter binding — **never** string
      concatenation or template-literal interpolation of user input into a
      query, for SQL or NoSQL (e.g. MongoDB operator injection via
      unsanitized `$where`/object-shaped input).
- [ ] Any shell command construction from user input is avoided entirely if
      possible; where unavoidable, uses an allowlist of permitted values and
      a library that passes arguments as an array (not a concatenated
      string) — never pass raw user input to `exec`/`system`/backticks.
- [ ] All input is validated server-side regardless of client-side
      validation (client-side is UX only, never the security boundary):
      type, format, length, and range checked for every field, not just
      "is it present."
- [ ] Enum-like fields (roles, statuses, categories, etc.) are checked
      against a closed allowlist, never accepted as freeform strings that
      later get trusted.
- [ ] Output is encoded/escaped for the context it's rendered into:
      HTML-encode for HTML body content, attribute-encode for HTML
      attributes, JS-string-encode for inline scripts, URL-encode for URL
      parameters. A templating engine with auto-escaping by default is
      strongly preferred over manual escaping.
- [ ] Any user-authored rich text / HTML is either (a) never rendered as
      raw HTML at all (rendered via a structured format + an explicit
      allowlisted-node renderer instead), or (b) sanitized through a
      well-maintained library (e.g. DOMPurify) with a strict allowlist of
      tags/attributes immediately before rendering — never trust a
      "sanitize on save" alone, since the render path is the actual attack
      surface.
- [ ] Link/URL fields accept only expected protocols (`http:`, `https:`,
      `mailto:`, etc.) — reject `javascript:`, `data:`, and `vbscript:`
      schemes, which are a common stored-XSS vector via seemingly-safe
      link fields.
- [ ] XML parsing (if any) disables external entity resolution (prevents
      XXE) and disables DTD processing where not needed.
- [ ] Deserialization of untrusted data uses a safe format (JSON with schema
      validation) rather than a language-native serialization format that
      can execute code on deserialize (e.g. Python `pickle`, Java native
      serialization, PHP `unserialize` on untrusted input).
- [ ] Any server-side request that fetches a URL derived from user input
      (webhooks, "fetch this image URL," link previews, etc.) validates
      against an allowlist of hosts/protocols and blocks requests to
      internal/private IP ranges and cloud metadata endpoints
      (`169.254.169.254`, `localhost`, RFC1918 ranges) — this is SSRF
      prevention.
- [ ] File paths built from user input are validated to prevent path
      traversal (`../`) — normalize and confirm the resolved path stays
      within the intended directory; prefer generating server-side
      filenames over trusting client-supplied ones at all.
- [ ] Template engines: confirm no user input reaches a template
      *compilation* step (as opposed to template *data*) — this is Server-
      Side Template Injection (SSTI), which is often full RCE.

## 5. Cryptography & Secrets Management

Maps to: OWASP ASVS V6, OWASP Top 10 A02:2021 (Cryptographic Failures),
CWE-321 (Hardcoded Crypto Key), CWE-326 (Inadequate Encryption Strength).

- [ ] All data in transit uses TLS 1.2+ (prefer 1.3), with weak ciphers/
      protocols (SSLv3, TLS 1.0/1.1, RC4, export ciphers) disabled at the
      server/load-balancer level.
- [ ] Sensitive data at rest (PII, financial data, health data, credentials)
      is encrypted using a current, vetted algorithm (AES-256-GCM or
      equivalent) — never a custom/home-rolled cipher.
- [ ] Secrets (API keys, DB credentials, signing keys, encryption keys) are
      never committed to version control. Confirm `.gitignore` covers
      `.env*` and any credentials file, and that `git log`/history doesn't
      already contain a leaked secret from before the ignore rule existed
      (a rotated key is required if one is found — removing it from a
      future commit doesn't remove it from history).
- [ ] Secrets are sourced from environment variables or a secrets manager
      (Vault, AWS/GCP/Azure secret managers, etc.), never hardcoded as a
      literal default (`SECRET = process.env.SECRET ?? "dev-secret"` is a
      finding — that fallback can silently ship to production).
- [ ] The app fails fast and loudly at startup if a required secret/env var
      is missing, rather than running with a weakened or undefined
      security posture.
- [ ] Cryptographic randomness (tokens, session IDs, password reset tokens,
      API keys) uses a CSPRNG (`crypto.randomBytes`,
      `crypto.getRandomValues`, `secrets` module, etc.) — never `Math.random()`
      or a language's default non-cryptographic PRNG for anything
      security-relevant.
- [ ] Signing keys (JWT, HMAC, cookie-signing) are of adequate length/
      algorithm strength, rotated periodically, and — for asymmetric JWTs
      — the verify step confirms the algorithm explicitly (never accept
      `alg: none`, and never let the client dictate which algorithm/key the
      server should verify with — the classic JWT `alg` confusion attack).
- [ ] Key management: encryption keys are stored separately from the data
      they protect, with restricted access, and there's a documented
      rotation plan.

## 6. API & Server-Side Security

Maps to: OWASP API Security Top 10, CWE-352 (CSRF), CWE-770 (Missing
Resource Limits).

- [ ] State-changing requests (POST/PUT/PATCH/DELETE, or any equivalent
      mutation) that rely on cookies for auth are protected against CSRF —
      via a framework's built-in same-origin/anti-CSRF-token mechanism, or
      an explicit CSRF token validated server-side. (Note: pure
      Authorization-header/bearer-token auth without cookies is inherently
      less CSRF-exposed, but confirm that's actually the auth model in use
      before relying on it as the mitigation.)
- [ ] CORS policy is an explicit allowlist of trusted origins — never
      `Access-Control-Allow-Origin: *` combined with
      `Access-Control-Allow-Credentials: true` (that combination leaks
      authenticated data to any origin).
- [ ] Rate limiting exists on all expensive or sensitive endpoints:
      authentication, password reset, search, anything calling a paid
      third-party API, and any endpoint that sends email/SMS (abuse/spam
      vector otherwise).
- [ ] Every endpoint that returns a list enforces pagination with a
      maximum page size — no endpoint can be asked to return an unbounded
      result set (DoS via resource exhaustion, and often an accidental
      mass-data-exposure vector).
- [ ] Request body size limits are enforced (prevents memory-exhaustion
      DoS from oversized payloads).
- [ ] API responses never include more data than the client needs —
      check for accidental over-fetching (returning a full internal user
      object including password hash/internal flags when only
      name+avatar were needed).
- [ ] HTTP methods are restricted to what each endpoint actually needs
      (no `TRACE`/`TRACK` enabled if unused; `OPTIONS` doesn't leak more
      than intended).
- [ ] Security headers are set: `Content-Security-Policy` (restricts
      script/style/resource origins — the strongest single XSS mitigation
      at the platform level), `X-Content-Type-Options: nosniff`,
      `X-Frame-Options: DENY` or `frame-ancestors 'none'` in CSP
      (clickjacking prevention), `Strict-Transport-Security` (HSTS, forces
      HTTPS on future visits), `Referrer-Policy` (avoid leaking sensitive
      URLs to third parties).
- [ ] GraphQL (if used): query depth/complexity limiting is in place
      (prevents a single deeply-nested query from causing a DoS), and
      introspection is disabled in production unless deliberately public.

## 7. File Upload / File Handling

Maps to: CWE-434 (Unrestricted Upload of Dangerous File Type), CWE-22
(Path Traversal).

- [ ] Uploaded file type is validated by **content** (magic-byte/signature
      sniffing), not just the client-supplied MIME type or file extension
      — both are trivially spoofable.
- [ ] File size is capped, enforced server-side.
- [ ] Uploaded files are stored with a server-generated name (random UUID
      or hash), never the client-supplied original filename — prevents
      path traversal and overwrite attacks via crafted filenames.
- [ ] Uploaded files are stored outside the web root, or in a location/
      configuration that prevents them from being executed as code (e.g.
      a script uploaded as an "image" should never be servable/executable
      by the web server).
- [ ] If uploads are served back to users, they're served with a
      `Content-Disposition` that prevents inline execution where
      appropriate, and with `X-Content-Type-Options: nosniff` so a
      mislabeled file isn't sniffed into an executable content type by
      the browser.
- [ ] Images/documents that get processed server-side (resizing, thumbnail
      generation, metadata extraction) use a current, patched library —
      image/document parsers are a common source of memory-corruption
      CVEs.
- [ ] Every file-handling endpoint independently checks authorization (see
      §3) — an upload/download endpoint is a common place for an access
      control check to be forgotten.

## 8. Error Handling & Logging

Maps to: OWASP ASVS V7, CWE-209 (Information Exposure Through Error
Message), CWE-532 (Insertion of Sensitive Info into Log File).

- [ ] Production error responses are generic and actionable to the
      *caller*, never a raw stack trace, internal file path, SQL error, or
      library version string — that detail goes to server-side logs only.
- [ ] Errors are mapped to the correct type/status: validation error,
      not-found, unauthorized, forbidden, conflict, rate-limited, server
      error — never everything collapsed into a generic 500.
- [ ] No secrets, passwords, full tokens, session IDs, or full card/PII
      data are ever written to logs — even at debug level. Redact/mask
      where a log needs to reference the *existence* of such data (e.g.
      log a user ID, not their email+password together).
- [ ] Logs include enough context to investigate an incident without
      reproducing it (request ID, user ID, operation name, timestamp) —
      but are structured, not raw request/response bodies dumped
      wholesale.
- [ ] Authentication failures, authorization failures, and other
      security-relevant events (password changes, role changes, account
      lockouts) are logged distinctly from routine application logs, so
      they can be monitored/alerted on.
- [ ] Logs are protected from tampering/deletion by the same users they
      might incriminate (write-once storage, centralized log shipping,
      restricted access to raw log files).
- [ ] No empty `catch` blocks, no silently swallowed exceptions — every
      caught error either handles the failure meaningfully or re-throws/
      logs it.

## 9. Dependency & Supply Chain Security

Maps to: OWASP Top 10 A06:2021 (Vulnerable and Outdated Components), NIST
SSDF PW.4.

- [ ] Dependency vulnerability scanning runs regularly (`npm audit`,
      `pip-audit`, Dependabot/Renovate, Snyk, or equivalent for the
      language ecosystem in use) — ideally gated in CI, not just run
      manually and forgotten.
- [ ] No dependency is pinned to a known-vulnerable version without an
      explicit, documented reason and a tracked follow-up to upgrade.
- [ ] Unmaintained/abandoned packages (no updates in years, single
      maintainer with no activity) are flagged, especially for
      security-relevant functionality (auth, crypto, parsing) — prefer a
      well-maintained alternative or the language's own standard library
      where one exists.
- [ ] Lockfiles (`package-lock.json`, `poetry.lock`, etc.) are committed,
      so builds are reproducible and a compromised upstream package version
      can't silently get pulled in.
- [ ] Build/CI pipeline itself is a supply-chain surface: third-party
      GitHub Actions/CI plugins are pinned to a commit SHA (not a mutable
      tag) where practical, and have only the permissions they actually
      need.
- [ ] `npm install`/build scripts from third-party packages aren't blindly
      trusted — consider `--ignore-scripts` or an allowlist approach for
      untrusted/low-reputation packages, since a package's install script
      runs arbitrary code.

## 10. Configuration & Infrastructure Hardening

Maps to: OWASP Top 10 A05:2021 (Security Misconfiguration), CIS Benchmarks.

- [ ] Debug mode, verbose error pages, and admin/dev tooling (e.g. a
      framework's debug console) are confirmed **off** in production —
      test this doesn't accidentally get re-enabled by an env var
      defaulting the wrong way.
- [ ] Default credentials on any component (database, admin panel,
      message queue, cache) are changed before deployment — grep infra
      config for default usernames like `admin`/`root` paired with a
      default or empty password.
- [ ] Unnecessary services/ports are disabled — the deployed surface
      exposes only what's actually needed (e.g. a database shouldn't be
      reachable from the public internet if only the app server needs it).
- [ ] Principle of least privilege applied to every service account/DB
      user/IAM role — a web app's DB user shouldn't have `DROP TABLE`
      rights if it only ever needs `SELECT`/`INSERT`/`UPDATE` on specific
      tables; a CI pipeline's cloud credentials shouldn't have
      account-wide admin access.
- [ ] Environment separation is real, not just naming — dev/staging/
      production use genuinely separate credentials, databases, and
      secrets; a staging leak shouldn't expose production data.
- [ ] Cloud storage buckets (S3 or equivalent) default to private, with
      public access explicitly opted into per-object/per-bucket only where
      truly needed, and that choice is periodically re-verified (bucket
      misconfiguration is one of the most common real-world breach causes).
- [ ] Directory listing is disabled on web servers; no `.git`, `.env`,
      backup files (`.bak`, `~`), or config files are reachable via a
      direct URL request.
- [ ] Software/OS/runtime versions are kept current with security patches
      — there's a defined process (not just "whenever someone notices"),
      even if lightweight for a small team.

## 11. Data Protection & Privacy

Maps to: GDPR/CCPA-style principles (apply proportionally to actual data
sensitivity and jurisdiction — not every app needs every control here),
OWASP ASVS V8.

- [ ] Personal data collected is limited to what's actually needed
      (data minimization) — don't collect/store a field "just in case."
- [ ] Sensitive PII (SSNs, full payment card numbers, health data) is
      never stored unless there's a genuine business need — for payment
      cards specifically, prefer a PCI-compliant processor/tokenization so
      raw card data never touches your own servers at all.
- [ ] There's a defined data retention policy, and a way to actually
      delete a user's data on request (not just soft-delete/hide it from
      the UI while it persists in the database indefinitely).
- [ ] Data exports/backups are encrypted and access-controlled the same as
      production data — a backup is not a lesser security boundary.
- [ ] Third-party analytics/tracking scripts don't receive PII
      inadvertently (e.g. an email address leaking into a URL that gets
      logged by an analytics provider).
- [ ] If the app serves users under applicable privacy regulations
      (GDPR, CCPA, etc.), confirm the legal/consent requirements
      (cookie consent, right-to-access, right-to-erasure) are actually
      implemented, not just described in a privacy policy.

## 12. Client-Side / Frontend Security

Maps to: OWASP ASVS V5, CWE-79 (XSS variants), CWE-1004.

- [ ] No sensitive data (auth tokens, PII) is stored in `localStorage` or
      `sessionStorage` if avoidable — these are readable by any script on
      the page (i.e. any XSS becomes full token theft). Prefer `HttpOnly`
      cookies for auth tokens specifically.
- [ ] A Content-Security-Policy is set restrictively enough to meaningfully
      reduce XSS impact (avoid `unsafe-inline`/`unsafe-eval` where
      possible; if genuinely needed, scope with nonces/hashes instead of a
      blanket allowance).
- [ ] Third-party scripts (analytics, chat widgets, ad tags) are loaded
      with Subresource Integrity (`integrity` attribute) where served from
      a CDN, so a compromised CDN can't silently inject malicious code.
- [ ] Client-side routing/state doesn't trust URL/query parameters as an
      authorization signal (e.g. `?role=admin` in the URL should never
      change what the UI *can* do, only at most what it optimistically
      *shows* pending a real server check).
- [ ] Autocomplete is disabled on sensitive fields where appropriate
      (`autocomplete="off"` on things like a one-time payment CVV), and
      password fields use `type="password"`.
- [ ] postMessage handlers (if used for cross-frame/cross-window
      communication) validate `event.origin` before trusting the message
      content.

## 13. Business Logic & Abuse Prevention

Maps to: OWASP Top 10 A04:2021 (Insecure Design).

- [ ] Multi-step workflows (checkout, signup, approval flows) can't be
      abused by skipping steps directly via a later-step API call (e.g.
      calling the "complete order" endpoint without having gone through
      payment validation).
- [ ] Numeric/quantity fields (price, quantity, discount %) are re-validated
      and re-derived server-side at the point of the actual transaction —
      never trust a client-submitted price or discount value.
- [ ] Race conditions in state-changing operations (e.g. redeeming a
      one-time coupon, withdrawing funds) are prevented via proper
      locking/transactions/idempotency keys — test what happens if the
      same request fires twice concurrently.
- [ ] Only idempotent operations are safely retryable; write/payment
      operations use an idempotency key so a network-retry can't
      double-charge or double-create.
- [ ] Automated abuse (scraping, credential stuffing, bulk account
      creation) is mitigated at the points that matter — rate limiting,
      CAPTCHA on high-value actions, anomaly detection on login patterns.

## 14. CI/CD & Deployment Security

Maps to: NIST SSDF PO/PS control families, SLSA framework principles.

- [ ] CI/CD secrets (deploy keys, cloud credentials) are stored in the
      CI platform's secret store, never in the repo or in plaintext
      pipeline config.
- [ ] Production deployment requires review/approval (branch protection,
      required PR review) — no direct unreviewed push to a branch that
      auto-deploys to production.
- [ ] The build pipeline itself runs security checks (dependency scan,
      secret scan, and ideally SAST — static analysis) as a gate, not just
      as an optional/manual step.
- [ ] Rollback capability exists and is tested — a bad deploy (including a
      security regression) can be reverted quickly.
- [ ] Infrastructure-as-code (Terraform, CloudFormation, etc.), if used,
      is itself scanned for misconfiguration (public S3 buckets, overly
      permissive security groups/firewall rules) before apply.

## 15. Third-Party Integrations

Maps to: OWASP ASVS V9, general vendor risk management.

- [ ] Webhooks received from third parties verify a signature (HMAC or
      equivalent) before trusting the payload — never process a webhook
      body as authoritative without verifying it actually came from the
      claimed sender.
- [ ] API keys for third-party services are scoped to the minimum
      permission the integration actually needs (a read-only key where
      only reads happen), and stored/rotated per §5.
- [ ] Data sent to third-party services (analytics, error-tracking tools
      like Sentry, AI APIs) is reviewed for accidental PII/secret leakage
      — e.g. confirm error-tracking scrubs request bodies/headers before
      upload.
- [ ] SDKs/libraries for third-party services are kept current (same as
      §9) — a vulnerable SDK is as much a supply-chain risk as any other
      dependency.

## Appendix: Standards Referenced

- **OWASP Top 10 (2021)** — the ten most critical web application risk
  categories, industry-standard starting point.
- **OWASP ASVS (Application Security Verification Standard)** — a much
  more granular, testable checklist (v4+ has ~280 requirements across 14
  categories); this doc pulls from and summarizes its most impactful items
  rather than reproducing it in full. Consult ASVS directly for a
  Level 2/3 (higher-assurance) audit.
- **OWASP API Security Top 10** — API-specific risk categories (broken
  object-level authorization, broken authentication, excessive data
  exposure, lack of rate limiting, etc.) — most already folded into §3/§6
  above.
